## 수행 기록

### 0. 접속

```bash
ssh k8s-1
```

접속 직후 `clear`가 실패했다 → [`incidents/2026-09-10-terminfo-xterm-ghostty.md`](incidents/2026-09-10-terminfo-xterm-ghostty.md)

### 1단계 — 사설 IP (실패가 정상)

```bash
# k8s-1 에서
ping -c3 -W1 10.0.0.169

# k8s-2 에서
ping -c3 -W1 10.0.0.155
```

**결과: 양방향 모두 실패.**

예상대로다. 두 노드가 같은 `10.0.0.0/24`를 쓰지만 서로 다른 VCN이라 경로 자체가 없다.
방화벽 문제가 아니다.

### 2단계 — 공인 IP tcp/22 (대조군)

```bash
# k8s-1 에서
ubuntu@k8s-1:~$ nc -vz 198.51.100.22 22
Connection to 198.51.100.22 22 port [tcp/ssh] succeeded!
```

```bash
# k8s-2 에서
nc -vz 203.0.113.11 22
```

**결과: 양방향 모두 성공.**

이것이 대조군이다. 경로 자체는 살아 있으므로, 이후 51820이 실패하면
원인이 **그 포트의 보안 목록 규칙**으로 좁혀진다. 라우팅이나 경로 가능성은 배제된다.

> 처음에는 2단계를 k8s-1 → k8s-2 한 방향만 했다.
> "맥에서 k8s-1로 SSH가 되니 반대 방향도 될 것"이라는 판단이 있었는데 **틀렸다.**
> 보안 목록 규칙에는 소스 CIDR이 붙으므로 출발지가 다르면 다른 테스트다.
> 대조군은 **본 테스트와 같은 방향**이어야 통제된 변수가 된다. 그래서 반대 방향도 측정했다.

### 3·4단계 — UDP 51820

**미실행.** OCI 콘솔에서 보안 목록 규칙을 넣어야 하는데 아직 하지 않았다.

Stage 1~3은 k8s-2 내부에서만 이뤄져 노드 간 네트워크가 필요 없으므로,
이 검증은 **Stage 8로 미뤘다.**

이월 항목:

| 항목 | 상태 |
|---|---|
| OCI 보안 목록에 UDP 51820 인그레스 (양쪽 VCN, 소스는 상대 공인 IP `/32`) | ⬜ |
| k8s-1 → k8s-2 통과 확인 (수신 측 `tcpdump`) | ⬜ |
| k8s-2 → k8s-1 통과 확인 (수신 측 `tcpdump`) | ⬜ |

> 미룬 것이 위험을 키우지는 않는다. Stage 8에서 막히더라도 그때까지 만든
> k8s-2 쪽 클러스터는 그대로 살아 있고, 최악의 경우 3노드로 계속 갈 수 있다.

## 배운 것

- **사설 IP는 전역 고유하지 않다.** 같은 대역이어도 다른 네트워크면 못 만난다.
- **대조군은 같은 방향이어야 한다.** 출발지가 다르면 다른 테스트다. 이걸 한 번 틀렸다.
- **`ping` 실패로 단정하면 안 된다.** OCI는 ICMP를 부분 허용하므로 TCP는 되는데 ping만 안 될 수 있다.
  그래서 공인 IP 확인은 `ping`이 아니라 `nc`로 했다.
- 진짜 문제는 연결이 아니라 **주소**였다 → [`notes/network/concepts/02_node-addressing.md`](../notes/network/concepts/02_node-addressing.md)
