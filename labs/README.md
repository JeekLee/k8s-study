# 실습 기록

**실제로 무엇을 했고 어떻게 됐는가.** 계획이나 개념이 아니라 *결과*를 남기는 곳.

## 세 영역의 구분

| 영역 | 성격 | 시제 | 예시 |
|---|---|---|---|
| [`docs/`](../docs/) | 설계와 계획 | 앞으로 할 것 | "Stage 4에서 MTU를 1370으로 맞춘다" |
| [`notes/`](../notes/) | 개념과 참고 자료 | 항상 참인 것 | "`AllowedIPs`는 수신 필터도 겸한다" |
| **`labs/`** | **실습 결과** | **한 것** | "MTU 1500으로 두고 돌렸더니 이미지 pull만 멈췄다" |

같은 주제가 세 곳에 나타날 수 있고, 그게 맞다.
계획은 `docs/`, 원리는 `notes/`, 실제로 겪은 것은 `labs/`.

## 구조

```
labs/
├── stage-NN-주제.md    Stage별 수행 기록
├── incidents/          예기치 않게 겪은 문제
└── drills/             의도적으로 고장내고 복구하는 훈련 (Stage 6)
```

## 수행 기록

실제로 실행한 명령과 출력. 문서의 예시가 아니라 **내가 친 것**을 적는다.
값을 바꿔 넣었다면 왜 바꿨는지도.

## 막힌 것

증상 → 확인 → 원인 → 해결. 여러 건이면 나눠서.
**아니었던 가설도 적는다.** 그게 다음에 시간을 아껴준다.

## 템플릿 — 고장 복구 훈련 (`drills/`)

CKA Troubleshooting은 배점 30%다. **시간을 재는 것**이 핵심이다.

```markdown
# 훈련: <무엇을 고장냈나>

| | |
|---|---|
| 일자 | YYYY-MM-DD |
| 소요 | N분 |
| 스냅샷 | 있음 / 없음 |

## 고장 주입
정확히 무엇을 했는가. 나중에 재현할 수 있도록.

## 관찰된 증상
사용자 입장에서 보이는 것. 에러 메시지 원문.

## 진단 경로
실제로 밟은 순서. **틀린 가설과 헛짚은 것을 포함해서.**
어느 명령이 결정적이었는지 표시.

## 원인

## 복구

## 다음에 더 빨리 하려면
어느 단계를 건너뛸 수 있었나. 어느 명령을 먼저 쳤어야 했나.
```

## 원칙

1. **내가 직접 한 것만 적는다.** 자동화 스크립트나 보조 도구가 수집한 값은
   여기가 아니라 [`docs/`](../docs/)로 보내거나, 남긴다면 출처를 명시한다.
   섞이면 "내가 해본 것"과 "누가 알려준 것"이 구분되지 않아 기록의 가치가 사라진다.
2. **출력을 붙여넣는다.** 요약하지 말고 원문을. 프롬프트까지 그대로면 더 좋다.
   나중에 다시 볼 때 요약은 쓸모가 없다.
3. **실패를 지우지 않는다.** 헛짚은 가설이 다음번의 지름길이다.
4. **시간을 잰다.** 특히 `drills/`. 아는 것과 2시간 안에 하는 것은 다르다.
5. **바로 적는다.** 끝나고 정리하려면 이미 잊는다.
6. **공인 IP·호스트명은 문서화 전용 값으로 치환한다.** 공개 저장소다.
