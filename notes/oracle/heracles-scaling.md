# HEracles 확장성 실측

> **출처 표시.** 이 문서의 수치는 **Claude 가 측정한 것**이다 (2026-09-15).
> 사용자가 직접 실행한 기록은 [`labs/`](../../labs/) 에 있다.
> 목적은 [Stage 5](../../docs/stages/stage-05-db-scaling.md) 설계가 유효한지
> **실습 전에 확인**하는 것이었다.

> **왜 그런지**는 [`heracles-query-model.md`](heracles-query-model.md) 에 있다.
> 이 문서는 수치와 측정 방법이다.

## 요약 — 샤딩은 유효하다

| 구성 | 인덱스 크기 | 쿼리 지연 |
|---|---|---|
| 단일 (1M 행) | 459 MB | **126 ms** |
| 샤드 1개 (250k 행) | 110 MB | **29.5 ms** |
| **4샤드 팬아웃** (동시 실행) | 4 × 110 MB | **29.5 ms** |

**4.27배 개선.** 결과 건수도 일치한다 (단일 20건 = 샤드 5+5+5+5).

근거가 되는 두 사실:

1. **검색 비용은 인덱스 크기에 선형이다**
2. **단일 검색은 단일 스레드로 1코어만 쓴다**

그래서 샤드를 K개로 나누면 **인덱스가 1/K** 이고 **K코어를 동시에** 쓴다.

| | |
|---|---|
| 호스트 | 32 vCPU / 251 GiB, x86_64 |
| DB | Oracle EE 26ai (`enterprise:23.26.1.0`), podman 5.7 rootless |

## 1. ⭐ `HERACLES_MATCH` 는 풀스캔이 아니다

```
EXPLAIN PLAN FOR SELECT id FROM bench WHERE HERACLES_MATCH(phone, '...') = 1;

| Id  | Operation                    | Name           |
|   0 | SELECT STATEMENT             |                |
|   1 |  TABLE ACCESS BY INDEX ROWID | BENCH          |
|   2 |   DOMAIN INDEX               | BENCH_PHONE_EX |
```

HEracles 는 **자체 FHE 인덱스(enWord)** 를 관리하고, 그것을 Oracle 의
**ODCI 도메인 인덱스**로 노출한다. Oracle Text 의 `CONTAINS()` 와 같은 구조다.

`install.sql` 의 주석이 그대로 말한다.

```
-- Same mechanism as Oracle Text's CONTAINS(): the optimizer walks the custom
-- domain index and gets result rowids through ODCIIndexStart/Fetch.
--   * only the search itself runs in ODCIIndexStart.
```

**따라서 Oracle Parallel Query 는 무관하다.** FHE 작업이 테이블 스캔에 없다.

### 컬럼 값은 AES, FHE 는 인덱스에만

```sql
name  RAW(2000) NOT NULL,   -- AES-256-GCM ciphertext
```

`heracles.encrypt()` 는 **AES-256-GCM** 이다. 빠르다.
**FHE 는 인덱스 쪽에 있고**, 비용도 거기 있다.

## 2. ⚠️ 처음 측정은 틀렸다 — 고유값이 고정이었다

첫 데이터셋은 전화번호를 `MOD(i, 10000)` 으로 만들었다.
행을 아무리 늘려도 **고유값은 1만 개로 고정**이다.

| N | 인덱스 | exact 검색 |
|---|---|---|
| 1,000 | 13 MB | 1.5 ms |
| 100,000 | 19 MB | 2.2 ms |
| 1,000,000 | 41 MB | 9.6 ms |

"행 100배에 지연 1.5배"로 보여서 **"샤딩은 이득이 없다"는 잘못된 결론**에 도달했다.
인덱스가 안 커졌으니 당연한 결과였다.

**전화번호를 유일값으로 바꾸자 전혀 다른 그림이 나왔다.**

| N | 인덱스 | exact 검색 (히트 1건 고정) |
|---|---|---|
| 100,000 | 57 MB | 10.67 ms |
| 1,000,000 | **459 MB** | **109.67 ms** |

**인덱스 10배 → 지연 10.3배. 선형이다.**

> **인덱스 크기는 행 수가 아니라 고유값 수를 따른다.**
> 같은 100만 행인데 고유값이 1만이면 41 MB, 100만이면 459 MB 다.

> ⚠️ **벤치마크를 설계할 때 카디널리티를 통제하지 않으면 결론이 뒤집힌다.**
> 이 실측에서 가장 값비싼 교훈이었다.

## 3. 비용 모델

히트 수를 바꿔가며 측정했다 (N=1,000,000, 인덱스 459 MB).

| 검색 | 히트 수 | 지연 |
|---|---|---|
| EXACT | 1 | 109.7 ms |
| PREFIX-12 | 10 | 73.7 ms |
| PREFIX-10 | 1,000 | 69.7 ms |
| PREFIX-8 | 10,000 | 92 ms |
| PREFIX-6 | 1,000,000 | **3,842 ms** |

같은 측정을 N=100,000 (57 MB) 에서도 했다.

| 검색 | 히트 수 | 지연 |
|---|---|---|
| EXACT | 1 | 10.7 ms |
| PREFIX-10 | 1,000 | 9.3 ms |
| PREFIX-8 | 10,000 | 37.3 ms |
| PREFIX-6 | 100,000 | 341 ms |

대략 이렇게 읽힌다.

```
지연 ≈ 0.22 ms × 인덱스_MB  +  3.7 µs × 히트_수
```

- **인덱스 항**이 기본 비용 — 히트가 1건이어도 459 MB 면 110 ms
- **히트 항**은 결과가 만 건을 넘을 때부터 지배적

> ⭐ **두 항 모두 샤딩으로 나뉜다.**
> 인덱스 항은 샤드당 1/K, 히트 항도 K개 샤드가 나눠 처리한다.

## 4. ⭐ 단일 검색은 단일 스레드다

검색 루프를 돌리며 `extproc` 프로세스를 샘플링했다.

```
%CPU=99.6  threads=1
%CPU=100   threads=1
%CPU=99.6  threads=1
...
```

**정확히 1코어, 스레드 1개.** 32코어 중 하나만 쓴다.

4세션을 동시에 돌리면 extproc 이 4개 뜬다 — **세션 1개 = extproc 1개 = 코어 1개.**

```
2646  99.7%  threads=1  extproc
2648  99.8%  threads=1  extproc
2656  99.7%  threads=1  extproc
2676  99.6%  threads=1  extproc
```

세션별 QPS 11.86~12.05 로 단일 세션(12.3)과 거의 같다 — **경합이 없다.**

`libheracles.so` 에 OpenMP 런타임은 없다 (`GOMP_*`, `omp_*` 심볼 0건).
OpenBLAS 가 정적 링크돼 있지만 검색 경로에서는 스레드를 쓰지 않는 것으로 보인다.

→ **한 쿼리의 지연은 코어를 더 줘도 줄지 않는다.** 샤딩이 유일한 수단이다.

## 5. 동시성 — 처리량은 샤딩 없이도 확장된다

같은 인덱스(1M)에 동시 세션을 늘리며 집계 QPS 를 쟀다.

| 동시 세션 | 집계 QPS | 세션당 QPS | 효율 |
|---|---|---|---|
| 1 | 12.3 | 12.30 | 100% |
| 2 | 24.6 | 12.30 | 100% |
| 4 | 48.0 | 12.00 | 98% |
| 8 | 90.8 | 11.35 | 92% |
| 16 | 146.5 | 9.16 | 74% |
| 32 | 165.7 | 5.18 | **42%** |

**8세션까지 92% 효율로 확장**하고, 32코어에서 **~166 QPS 로 포화**한다.

세션마다 `extproc` 이 따로 뜨므로 코어를 하나씩 가져간다.
16세션부터 효율이 떨어지는 것은 코어 경합과 메모리 대역폭 때문으로 보인다.

> **처리량이 목표라면 샤딩할 이유가 없다.** 한 인스턴스에 동시 세션만 늘리면 된다.
> **지연이 목표라면 동시성은 아무 도움이 안 된다.** 한 쿼리는 여전히 ~110 ms 다.

## 6. 샤딩 실측

1M 행을 `MOD(id,4)` 로 4등분했다. **암호문을 그대로 복사**하므로 재암호화가 없다.

```sql
CREATE TABLE bench_s0 AS SELECT * FROM bench WHERE MOD(TO_NUMBER(id),4) = 0;
```

각 샤드에 HEracles 인덱스를 따로 만들었다 (총 구축 20.7초).

| | 인덱스 | 지연 | 히트 |
|---|---|---|---|
| 단일 `bench` | 459 MB | **126 ms** | 20 |
| 샤드 `bs0` | 110 MB | **29.5 ms** | 5 |
| 샤드 `bs1` | 110 MB | 29.5 ms | 5 |
| 샤드 `bs2` | 110 MB | 29.5 ms | 5 |
| 샤드 `bs3` | 110 MB | 29.5 ms | 5 |
| **4샤드 동시 팬아웃** | | **29.5 ms** | 20 |

**126 → 29.5 ms, 4.27배.** 샤드 수(4)보다 약간 나은 것은
인덱스가 작아져 캐시 효율이 올라간 것으로 보인다.

동시에 실행해도 샤드별 지연이 그대로다 — **코어가 남으므로 경합이 없다.**

---

## 7. 부가 측정

| 항목 | 값 |
|---|---|
| AES 암호화 + INSERT | ~0.2 ms/행 (1M 행 196초) |
| FHE 인덱스 구축 | ~32 µs/행 (1M 행 32초). **선형** |
| 인덱스 크기 | 고유값당 ~460 바이트 + 고정 13 MB |
| **원본 컬럼 대비** | `phone` 원본(AES) **39.1 MB** vs FHE 인덱스 **450 MB** = **11.5배** |

인덱스 구축이 **선형이고 생각보다 빠르다.** 100만 행에 32초다.
샤드로 나누면 병렬 구축도 가능하다.

## 결론 — Stage 5 설계에 반영할 것

| 목표 | 수단 | 근거 |
|---|---|---|
| **지연 단축** | **샤딩** | 인덱스 ∝ 지연, 단일 스레드. **4샤드 = 4.3배** |
| **처리량 증대** | **동시 세션** | 한 인스턴스가 8세션까지 92%, 32코어 포화 |
| 인덱스 구축 단축 | 샤드별 병렬 구축 | 선형이므로 나눠짐 |

**Parallel Query(DOP)는 이 워크로드와 무관하다.** 도메인 인덱스라 테이블 스캔에 FHE 가 없다.

### 남은 질문

- 샤드를 **노드에 흩었을 때** — 지금은 한 호스트 안이라 네트워크가 없었다
- **8 / 16 샤드**에서도 선형인가 — 팬아웃 오버헤드가 언제 이기는가
- **키 공유** — 샤드마다 키가 다르면 안 된다 → [`heracles-install.md`](heracles-install.md)
- 쓰기(`append_json`) 경로의 확장성 — 측정하지 않았다
