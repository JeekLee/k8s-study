# HEracles 는 왜 그렇게 동작하는가

수치는 [`heracles-scaling.md`](heracles-scaling.md) 에 있다. 이 문서는 **왜 그런지**를 다룬다.

## 한 줄

**검색은 FHE 인덱스를 처음부터 끝까지 훑는 일이고, 그걸 코어 하나로 한다.**
샤딩은 인덱스를 K조각으로 쪼개 **K개 코어가 동시에** 훑게 만드는 것이다.

---

## 1. 인덱스를 못 쓰는 게 아니다 — 두 종류가 있다

| | 대상 | 동작 |
|---|---|---|
| **Oracle 인덱스** (B-tree 등) | **평문** 컬럼 | 정상. 100만 건도 20번 비교면 끝 |
| **HEracles FHE 인덱스** (enWord) | **암호화** 컬럼 | 쓴다. 다만 **탐색이 선형** |

**테이블은 풀스캔하지 않는다.**

```
| Id  | Operation                    | Name           |
|   1 |  TABLE ACCESS BY INDEX ROWID | BENCH          |   ← 필요한 행만 읽는다
|   2 |   DOMAIN INDEX               | BENCH_PHONE_EX |   ← 인덱스가 rowid 를 준다
```

100만 행 테이블에서 **1행만 읽는다.** 풀스캔이면 100만 행을 다 읽었을 것이다.

**전체를 훑는 것은 "인덱스 안에서" 다.**

## 2. ⭐ 왜 인덱스 안에서 가지치기가 안 되는가

일반 B-tree 는 이렇게 좁힌다.

```
"김" 을 찾는다
  → 중간값이 "박" 이다. 김 < 박 이므로 왼쪽만 본다      ← 절반을 버린다
  → 또 절반, 또 절반 …  20번이면 100만 건에서 찾는다
```

**암호문에서는 이 "김 < 박" 비교를 할 수 없다.**
한다면 그 순간 **순서 정보가 새어나가고**, 암호화한 의미가 사라진다.

> 서버가 암호문 상태로 "어느 쪽이 큰가"를 알 수 있다면 공격자도 알 수 있다.
> 순서 비교를 반복하면 원본 값을 상당 부분 복원할 수 있다.

**가지치기를 못 하는 것은 구현의 한계가 아니라 보안 속성이다.**
그래서 인덱스 전체를 훑는다.

측정이 이를 뒷받침한다 — **결과가 1건으로 고정인데 인덱스 10배에 시간 10.3배.**

> 이 조건의 측정점은 2개(57 MB, 459 MB)다. "선형"은 그 범위에서의 관찰이고
> 내부 알고리즘을 직접 확인한 것은 아니다.

### 그래도 인덱스는 필수다

인덱스가 없으면 **행마다 복호화해서 비교**해야 한다. 훨씬 느리고,
복호화하는 순간 HEracles 를 쓰는 이유가 사라진다.


### ⭐ 인덱스가 원본보다 크다

"인덱스를 쓰면 덜 읽는다"는 직관이 여기서는 반대다. 실측이다.

| | 크기 |
|---|---|
| `phone` 컬럼 원본 (AES) | **39.1 MB** (행당 41 바이트 × 100만) |
| **FHE 인덱스** | **450 MB** |

**인덱스가 원본의 11.5배다.** 인덱스를 훑는 것이 컬럼을 훑는 것보다
**11배 더 많은 바이트를 읽는 일**이다.

그런데도 인덱스를 만드는 이유는 하나다.

```
phone 컬럼 = AES-256-GCM 암호문
  → 39 MB 를 다 읽어도 "이게 010-1234-5678 인가" 를 판단할 수 없다
  → 판단하려면 복호화해야 한다
  → 복호화하는 순간 평문이 서버에 노출된다        ← 쓰는 이유가 사라진다
```

FHE 인덱스는 **복호화 없이 비교가 가능한 형태**로 다시 저장한 것이다.
그 대가가 11배 크기다.

### 이름이 오해를 부른다

| | 목적 | 결과 |
|---|---|---|
| **일반 B-tree 인덱스** | **적게 읽으려고** | 100만 건 → 20번 비교 |
| **FHE 인덱스** | **읽을 수 있게 하려고** | 전수 조사, 크기는 11배 |

이름은 같지만 하는 일이 정반대다.
일반 인덱스는 **탐색 공간을 줄이는** 도구이고,
FHE 인덱스는 **연산을 가능하게 하는** 도구다.

### 그래서 일반적인 수단이 안 통한다

| 수단 | 왜 안 되나 |
|---|---|
| 인덱스 추가 | 이미 쓰고 있고, 그것이 전수 조사 대상이다 |
| 더 선택적인 조건 | 조건이 선택적이든 아니든 인덱스는 전부 훑는다 |
| Parallel Query | 쪼갤 테이블 스캔이 없다 |
| 코어 늘리기 | 단일 스레드라 1개만 쓴다 |

**전수 조사를 피할 수 없으므로 남은 지렛대는 둘뿐이다.**

```
① 한 번에 훑을 양을 줄인다   → 인덱스를 K조각으로
② 동시에 훑는다              → K개 코어에
```

샤딩이 이 둘을 동시에 한다. 그래서 4샤드에서 4.27배가 나온다.

## 3. 왜 코어를 더 줘도 한 검색은 안 빨라지는가

검색 중 프로세스를 샘플링한 결과다.

```
%CPU=99.6   threads=1
%CPU=100    threads=1
```

**스레드 1개, 코어 1개.** 호스트에 32코어가 있어도 **31개가 논다.**

```
┌──────────────────────────────────────┐
│ 코어1   ████████████  검색 중        │
│ 코어2   ░░░░░░░░░░░░  논다           │
│  …                                   │
│ 코어32  ░░░░░░░░░░░░  논다           │
└──────────────────────────────────────┘
```

**코어를 준다고 프로그램이 알아서 나눠 쓰지 않는다.**
`libheracles.so` 가 단일 스레드로 만들어져 있다 (OpenMP 런타임 심볼 0건).

그래서 **Oracle 의 Parallel Query 도 소용없다.** 병렬로 쪼갤 테이블 스캔 자체가 없다.

---

## 4. 샤딩이 하는 일 — 프로그램이 안 쪼개니 우리가 쪼갠다

데이터를 K등분해 **독립된 검색 K개**로 만든다. 그러면 서로 다른 코어에 올라간다.

**전**

```
검색 1회
  └── 459 MB 전체를 훑는다 ── 코어1 ── 126 ms
      (코어 2~32 는 논다)
```

**후**

```
검색 1회
  ├── 110 MB ── 코어1 ─┐
  ├── 110 MB ── 코어2 ─┤  동시에 출발
  ├── 110 MB ── 코어3 ─┤
  └── 110 MB ── 코어4 ─┘
       ↓
   가장 늦은 것 = 29.5 ms
       ↓
   결과 합치기 (5+5+5+5 = 20건)
```

이득이 두 겹이다.

| | |
|---|---|
| ① 각자 훑을 양이 **1/K** | 110 MB 만 보면 된다 |
| ② **동시에** 진행 | 순서대로가 아니라 한꺼번에 |

①이 ② 덕분에 **그대로 전체 시간이 된다.** 측정: **126 → 29.5 ms (4.27배)**

> 4배보다 약간 나은 것은 인덱스가 작아져 CPU 캐시 효율이 올라간 것으로 보인다.

## 5. 세션 · extproc · `limits.cpu`

### ⭐ 세션 1개 = extproc 1개 = 코어 1개

4세션을 동시에 돌리며 확인했다.

```
4세션 동시 검색 중
  2646  99.7%  threads=1  extproc
  2648  99.8%  threads=1  extproc
  2656  99.7%  threads=1  extproc
  2676  99.6%  threads=1  extproc      ← 정확히 4개
```

세션별 QPS 11.86~12.05 로 **단일 세션(12.3)과 거의 같다 — 경합이 없다.**

Oracle 이 **세션마다 extproc 에이전트를 따로 띄우기** 때문이다.
유휴 상태에서는 0개이고, 검색이 들어올 때 생긴다.

### 세션을 늘리는 법

**세션 = DB 커넥션이다.** 앱의 커넥션 풀 크기가 곧 동시 세션 수다.

```yaml
# Spring Boot
spring.datasource.hikari.maximum-pool-size: 8
```

```python
# SQLAlchemy
create_engine(dsn, pool_size=8, max_overflow=0)
```

**이게 전부다.** 인스턴스를 늘릴 필요도, 데이터를 나눌 필요도 없다.

### ⚠️ `limits.cpu` 가 진짜 상한이다

검색 하나가 코어 하나를 다 쓰므로:

```yaml
resources:
  limits: { cpu: "8" }      # → 동시에 8개까지만 실제로 돈다
```

8을 넘는 세션은 **연결은 되지만 CPU 를 기다린다.**
커넥션 풀만 20으로 키워도 소용없다.

> **커넥션 풀 크기 ≈ `limits.cpu`** 로 맞추는 것이 맞다.
> Oracle 쪽 `processes`/`sessions` 파라미터도 그보다 커야 한다.
> ```sql
> SHOW PARAMETER processes;
> ```

## 6. 평문 조건을 같이 쓰면 — FHE 비용은 안 줄어든다

`WHERE HERACLES_MATCH(...)=1 AND <평문 조건>` 을 실측했다 (100만 행, 인덱스 459 MB).

| 쿼리 | 지연 | 평문 조건 통과율 |
|---|---|---|
| FHE 단독 | 144 ms* | — |
| FHE AND `active='Y'` | **75.3 ms** | 90% |
| FHE AND `grp=7` (인덱스 있음) | **75.3 ms** | 0.1% |
| FHE AND `id='…'` (PK, 1건) | **76 ms** | 0.0001% |
| 평문만 `grp=7` | 0.7 ms | — |
| 평문만 PK 1건 | 0 ms | — |

<sub>*첫 실행이라 캐시 워밍 포함</sub>

**평문 조건이 90% 를 통과시키든 0.0001% 를 통과시키든 75 ms 로 같다.**
평문만 쓰면 0.7 ms 이므로 **FHE 가 75 ms 를 전부 차지한다.**

### 실행계획이 이유를 보여준다

```
| 1 |  TABLE ACCESS BY INDEX ROWID BATCHED | BENCH          |
| 2 |   BITMAP CONVERSION TO ROWIDS        |                |
| 3 |    BITMAP AND                        |                |   ← 교집합
| 4 |     BITMAP CONVERSION FROM ROWIDS    |                |
| 5 |      INDEX RANGE SCAN                | BENCH_GRP      |   ← 평문 인덱스
| 6 |     BITMAP CONVERSION FROM ROWIDS    |                |
| 7 |      SORT ORDER BY                   |                |
| 8 |       DOMAIN INDEX                   | BENCH_PHONE_EX |   ← FHE, 항상 전부 실행
```

**둘을 각각 끝까지 돌린 뒤 교집합을 낸다.** `OR` 이면 `BITMAP OR` 이고 역시 둘 다 돈다.

순서를 바꿀 수 없는 것은 **인터페이스 때문**이다.
`ODCIIndexStart` 는 검색값만 받고 **매칭 rowid 전부**를 돌려준다.
"이 1,000개 rowid 중에서만 찾아라" 를 전달할 방법이 없다.

```
일반 DB   WHERE a=1 AND b=2
          → 선택적인 쪽을 먼저, 그것으로 좁힌 뒤 나머지 확인      ✅

FHE       WHERE HERACLES_MATCH(...)=1 AND grp=7
          → FHE 전부 실행  +  grp 인덱스 조회  →  교집합          ❌ 좁히기 불가
```


### ⚠️ 쿼리를 고쳐서 순서를 바꿀 수는 없다

"평문 조건을 먼저 적용하게 힌트를 주면 되지 않나" 는 **원리적으로 불가능하다.**

`HERACLES_MATCH` 의 **함수형 구현이 항상 오류를 던지기 때문**이다.

```sql
-- install.sql
-- Functional implementation: called without a domain index there is no way to
-- evaluate FHE on plaintext, so raise.
CREATE OR REPLACE FUNCTION heracles_match_fn(p_col VARCHAR2, p_query VARCHAR2)
  RETURN NUMBER IS
BEGIN
    raise_application_error(-20823,
      'HERACLES_MATCH requires a domain index (heracles_indextype) to be usable');
END;
```

**도메인 인덱스로만 평가된다.** 행 단위 평가가 아예 없다.

| 시도 | 결과 |
|---|---|
| `WHERE grp=7 AND HERACLES_MATCH(...)` 순서 바꾸기 | SQL 에서 순서는 무의미. 옵티마이저가 정한다 |
| `/*+ NO_INDEX(bench bench_phone_ex) */` | **ORA-20823 오류** |
| 서브쿼리로 먼저 좁히고 밖에서 FHE | 여전히 도메인 인덱스 경로. 비용 동일 |
| 인라인 뷰 + `NO_MERGE` 로 실체화 | 위와 같다 |

#### 벤더가 이 상황을 방어해뒀다

`install.sql` PART C 의 주석이 설계 의도를 그대로 말한다.

```
-- Why this exists: heracles_match_fn (the functional implementation) always raises
-- ORA-20823, so a plan that does NOT walk the domain index does not merely run
-- slowly -- it fails.  Giving the CBO a cost and a selectivity for HERACLES_MATCH
-- is what keeps the domain-index path chosen once the predicate is ANDed with
-- other predicates or pulled into a join.
```

평문 조건과 AND 되거나 조인에 끌려 들어갔을 때 옵티마이저가 다른 계획을 고르면
**느려지는 게 아니라 실패**하므로, 통계 타입(`ODCIStats`)을 등록해
**도메인 인덱스가 항상 선택되도록 비용을 조작**해둔 것이다.

> 그 비용값은 실측이 아니라 `heracles_stats_cfg` 테이블의 placeholder 다.
> ```
> -- Placeholder numbers: ... Retune from measurements before treating these as real.
> ```
> 조정할 수 있지만 **더 싸게 만드는 방향으로만** 의미가 있다.
> 비싸게 만들면 다른 계획을 골라 오류가 난다.

#### 왜 원리적으로 안 되는가

```
grp=7 로 1,000건을 먼저 추렸다고 하자
  → 각 행의 phone 은 AES 암호문
  → 비교하려면 복호화해야 한다          ← 목적 위배
  → 아니면 FHE 인덱스를 거쳐야 한다      ← 그건 전체 인덱스 조회
```

**FHE 검색은 "인덱스 전체" 를 단위로만 성립한다.** 부분 집합에 대해 실행할 수 있는 형태가 아니다.

```
쿼리 레벨    ❌  힌트·순서·서브쿼리 전부 불가
스키마 레벨  ✅  평문 컬럼으로 샤딩 → 조회할 인덱스 자체를 줄인다
```

**"어떤 인덱스를 볼지" 는 정할 수 있고, "인덱스 안에서 어디를 볼지" 는 불가능하다.**

### ⭐ 우회로 — 샤딩 키를 평문 필터 컬럼으로

**인덱스 하나 안에서는 못 좁히지만, 인덱스를 나눠두면 된다.**

```
지금      FHE 인덱스 1개 (전체)       →  grp=7 조건이 도움이 안 된다

샤딩 후   grp 0~99    → 샤드0 인덱스
          grp 100~199 → 샤드1 인덱스
           …
          grp=7 이면 샤드0만 조회      →  FHE 비용 1/K
```

**평문 필터 컬럼을 샤딩 키로 잡으면 그 조건이 샤드 프루닝이 된다.**
일반 DB 의 파티션 프루닝과 같은 효과다.

| 샤딩 키 | 효과 |
|---|---|
| 무작위 (`MOD(id,K)`) | 전 샤드 팬아웃. **지연 1/K** (측정: 4샤드 4.27배) |
| **자주 쓰는 평문 필터** | **해당 샤드만 조회.** 지연 1/K 이면서 **코어도 1개만 쓴다** |

두 번째가 훨씬 낫다. 팬아웃이 없고, 나머지 샤드는 다른 요청을 처리할 수 있다.

> **예 — 테넌트별 검색이면 `tenant_id` 로 샤딩한다.**
> `WHERE tenant_id = X AND HERACLES_MATCH(...)` 가 해당 테넌트 인덱스만 본다.

### 정리

| 하려는 것 | 되나 |
|---|---|
| 평문 조건으로 **FHE 비용** 줄이기 | ❌ 불가. 선택도와 무관하게 전부 실행된다 |
| 평문 조건으로 **결과 건수** 줄이기 | ✅ 된다. 테이블 액세스·전송이 싸진다 |
| **평문 컬럼으로 샤딩해 프루닝** | ✅ **이것이 정답** |
| FHE 조건 두 개 AND | ⚠️ 측정하지 않았다. **둘 다 실행될 가능성이 높다** |

## 7. 복합 검색 — 조건이 여러 개면 비용은 **더해진다**

100만 행(`bench`, 인덱스 811 MB, phone+name 2컬럼)과
10만 행(`bench2`, 인덱스 ~50 MB, phone) 로 측정했다. 워밍업 3회 후 15회 평균.

### 7-1. 같은 테이블에 FHE 조건 여러 개

| 쿼리 | 지연 |
|---|---|
| `phone` 단독 | 74.7 ms |
| `name` 단독 | 58.7 ms |
| **`phone` AND `name`** | **136.7 ms** ≈ 74.7 + 58.7 |
| `phone` OR `name` | 137.3 ms (AND 와 같다) |
| `phone` AND 평문 `grp=7` | 74.0 ms (평문은 공짜) |

**조건 두 개면 두 번 검색한다. 서로를 좁혀주지 않는다.**
`AND` 든 `OR` 든 같다 — `BITMAP AND` / `BITMAP OR` 만 다르고 양쪽 도메인 인덱스는 전부 돈다.

### 7-2. 조인

| 쿼리 | 지연 |
|---|---|
| 조인만 (평문 `grp=7`) | **0.7 ms** |
| 조인 + `bench` 쪽만 FHE | 76.7 ms |
| 조인 + `bench2` 쪽만 FHE | 7.3 ms |
| **조인 + 양쪽 FHE** | **86.7 ms** ≈ 76.7 + 7.3 |
| `bench` 단독 FHE (기준) | 76.7 ms |
| `bench2` 단독 FHE (기준) | 7.3 ms |

**조인은 FHE 비용에 아무것도 더하지 않는다.** 단독 검색과 정확히 같다.
조인 자체(0.7 ms)는 사실상 공짜다.

### 7-3. ⭐ 비용 모델

```
총 지연  ≈  Σ (FHE 조건별 비용)  +  일반 SQL 비용(대개 무시 가능)

FHE 조건 비용  ≈  0.24 ms/MB × 그 인덱스 크기  +  3.7 µs × 히트 수
```

| 요소 | 비용 |
|---|---|
| FHE 조건 1개 | 인덱스 크기에 비례 |
| FHE 조건 N개 | **N개의 합** (곱이 아님 — 그나마 다행) |
| 평문 조건 | **0** (선택도 무관) |
| 조인 | **0** (FHE 비용에 영향 없음) |
| 일반 인덱스 여러 개 | 0 |

### 7-4. 컬럼을 추가해도 기존 검색은 안 느려진다

`bench` 의 FHE 인덱스를 `phone` 1컬럼에서 `phone`+`name` 2컬럼으로 바꿔봤다.

| | 1컬럼 | 2컬럼 |
|---|---|---|
| 인덱스 크기 | 450 MB | **811 MB** |
| 구축 시간 | 32 초 | 38.5 초 |
| **`phone` 검색** | 75 ms | **74.7 ms** |

**크기는 1.8배가 됐는데 `phone` 검색은 그대로다.**
enWord 인덱스가 **컬럼별로 분리 저장**되어, 한 컬럼을 검색할 때 다른 컬럼 몫을 내지 않는다.

> 구축 시간이 2배가 아니라 1.2배인 것도 같은 맥락으로 보인다
> (행 순회는 한 번, 컬럼별 처리만 추가).

### 7-5. 설계 지침

| 하려는 것 | 판단 |
|---|---|
| FHE 컬럼을 여러 개 인덱싱 | ✅ **괜찮다.** 안 쓰는 컬럼은 비용에 영향 없다 |
| 한 쿼리에 FHE 조건 여러 개 | ⚠️ **비용이 합산된다.** 꼭 필요한 것만 |
| FHE 조건 + 평문 조건 | ✅ 평문은 공짜 |
| FHE 조건 + 조인 | ✅ 조인은 공짜 |
| 작은 테이블에 FHE | ✅ **싸다** (10만 행 7.3 ms vs 100만 행 76.7 ms) |

**FHE 조건은 한 쿼리에 하나로 유지하는 것이 가장 좋다.**
두 값을 모두 만족하는 행을 찾아야 한다면, **두 값을 합친 컬럼을 따로 두고
거기에 인덱스를 거는 것**이 조건 두 개를 AND 하는 것보다 싸다.

```sql
-- 비싼 방식: 조건 두 개 (합산 비용)
WHERE HERACLES_MATCH(phone,:1)=1 AND HERACLES_MATCH(name,:2)=1     -- 136.7 ms

-- 싼 방식: 합친 값 하나를 인덱싱
--   phone_name = heracles.encrypt(phone || '|' || name)
WHERE HERACLES_MATCH(phone_name, :1)=1                             -- ~75 ms 예상
```

> 다만 합친 컬럼은 **정확히 그 조합으로만** 검색할 수 있다.
> 쿼리 패턴이 고정적일 때만 유효하다.

## 8. 언제 무엇을 하는가

```
샤딩 = 인덱스를 나눈다    →  한 검색이 빨라진다
복제 = 인덱스를 복사한다  →  더 많이 처리한다
```

| 상황 | 해야 할 것 |
|---|---|
| 한 검색이 110 ms 라 느리다 | **샤딩** |
| 동시 사용자가 8명 정도 | 커넥션 풀만. **파드 1개** |
| 동시 사용자가 30명 이상 | `limits.cpu` 올리기. **파드 1개** (~166 QPS 까지) |
| **166 QPS 를 넘는다** | **읽기 복제본** — 같은 인덱스를 가진 파드를 여러 개 |
| 둘 다 문제 | 샤딩 × 복제 |

**복제본은 데이터를 나누지 않는다.** 똑같은 인덱스를 가진 인스턴스를 여러 개 두고
앞에 로드밸런서를 놓는다. **지연은 그대로 110 ms** 지만 처리량이 인스턴스 수만큼 는다.

## 9. ⚠️ 먼저 확인할 것 — 카디널리티

**인덱스 크기는 행 수가 아니라 "서로 다른 값이 몇 개인가" 로 정해진다.**

같은 100만 행인데:

| 서로 다른 값 | 인덱스 | 검색 |
|---|---|---|
| 10,000 | 41 MB | 9.6 ms |
| 1,000,000 | 459 MB | 109.7 ms |

**11배 차이다.**

전화번호처럼 다 다른 값이면 인덱스가 크고, 도시명처럼 몇 가지뿐이면 작다.

```sql
-- 검색할 컬럼의 고유값 수를 먼저 본다
SELECT COUNT(DISTINCT phone_plain) FROM 원본테이블;
```

**고유값이 적으면 인덱스가 작아 검색이 이미 빠르다. 샤딩할 이유가 없다.**
