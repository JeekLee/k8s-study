# 02. `nc` (netcat) — 포트가 열려 있는가 (L4)

이름 그대로 **`cat`의 네트워크 버전**이다.
`cat`이 파일을 읽어 표준출력으로 흘려보내듯, `nc`는 **네트워크 연결을 파이프처럼** 다룬다.
표준입력으로 들어온 걸 소켓으로 보내고, 소켓에서 온 걸 표준출력으로 뱉는다.

그게 전부인데, 그 단순함 때문에 네트워크 진단의 만능 도구가 된다.

Ubuntu 기본은 `netcat-openbsd` 구현이다. 배포판마다 옵션이 조금씩 다르니 `man nc`로 확인할 것.

## 두 가지 모드

```bash
nc <호스트> <포트>      # 클라이언트 — 접속하러 간다
nc -l <포트>            # 서버 — 접속을 기다린다
```

직접 해보면 감이 온다. 실제로 연결되는 것이라 SSH 배너가 그대로 나온다:

```bash
nc 198.51.100.22 22
# → SSH-2.0-OpenSSH_9.x Ubuntu...
# Ctrl+C 로 빠져나옴
```

## 옵션

| 옵션 | 뜻 |
|---|---|
| `-v` | verbose — 결과를 문장으로 알려줌 |
| `-z` | zero-I/O — **데이터를 안 보내고** 연결만 시도한 뒤 즉시 끊음 |
| `-u` | UDP 사용 (기본은 TCP) |
| `-l` | 리스너로 동작 |
| `-w` | 타임아웃(초) |
| `-n` | 이름 해석 안 함 |

`-z`가 없으면 연결한 채로 계속 대기한다(위 SSH 배너 예시처럼).
포트가 열렸는지만 확인할 땐 `-z`를 붙여 바로 빠져나오게 한다.

```bash
nc -vz -w3 198.51.100.22 22
# → Connection to 198.51.100.22 22 port [tcp/ssh] succeeded!
```

## ⭐ `ping` 대신 `nc`를 쓰는 이유

둘은 **다른 계층**을 본다.

| | 계층 | 확인하는 것 |
|---|---|---|
| `ping` | L3 (ICMP) | 그 **호스트**에 IP가 닿는가 |
| `nc` | L4 (TCP) | 그 **포트**가 열려 있는가 |

호스트에는 닿는데 특정 포트만 막힌 경우가 아주 흔하다.
Phase 0 상황이 정확히 그렇다 — 22번은 열려 있고 51820은 막혀 있다.
`ping`으로는 이 차이를 구분할 수 없다.

## 실전 팁 — `-w`를 항상 붙일 것

방화벽이 막는 방식은 두 가지다.

| 방식 | 동작 | `nc` 반응 |
|---|---|---|
| **REJECT** | 거부 응답을 돌려줌 | 즉시 `Connection refused` |
| **DROP** | 조용히 폐기, 응답 없음 | 타임아웃까지 **멈춤** |

`-w3`으로 3초 후 포기하게 한다. 그리고 이 차이 자체가 단서다 —
**빨리 실패하면 REJECT, 오래 멈추면 DROP.** 방화벽 정책을 추측할 수 있다.

## ⚠️ UDP에서는 믿을 수 없다

```bash
nc -vzu <호스트> 51820   # ← 이 결과를 믿지 말 것
```

UDP는 연결 개념이 없어서 **응답이 없어도 성공으로 표시**된다. 거짓 성공이다.

UDP 확인은 반드시 **받는 쪽에서** 한다:

```bash
# 받는 쪽 — 리스너 또는 tcpdump
nc -u -l 51820
sudo tcpdump -ni ens3 udp port 51820

# 보내는 쪽
echo hello | nc -u -w2 198.51.100.22 51820
```

## 기타 활용

```bash
# 두 터미널 사이 채팅 (연결 확인용)
nc -l 9000                    # A
nc <A의 IP> 9000              # B — 타이핑하면 서로 보임

# 임시 리스너를 띄워 방화벽 통과 테스트
nc -l 6443                    # 아직 서비스가 없는 포트로 미리 확인

# 파일 전송
nc -l 9000 > received.tar     # 받는 쪽
nc <IP> 9000 < send.tar       # 보내는 쪽
```
