# WireGuard — 참고 자료

> 🔍 **검토 중 · 채택 확정 아님**
> [노드 주소 문제](../concepts/02_node-addressing.md)의 해결 후보 중 하나다.
> 장단점과 대안은 문서 하단 [검토 메모](#검토-메모)에 정리했다.

## 무엇인가

두 대의 컴퓨터 사이에 **암호화된 가상 랜선**을 놓는 VPN이다.

켜면 `wg0`라는 **가상 네트워크 인터페이스**가 생긴다. `ens3` 같은 진짜 랜카드처럼
IP를 갖고 `ip addr`에도 나오지만 실제 하드웨어는 없다.

```
[k8s-1]                                      [k8s-2]
10.10.0.1                                    10.10.0.2

  ① 앱이 10.10.0.2로 패킷 전송
      ↓
  wg0 ── ② 암호화하고 UDP로 포장
      ↓
  ens3 (10.0.0.155)
      ↓
  ③ 공용 인터넷 ── UDP 51820 ──────────────► ens3 (10.0.0.169)
                                                  ↓
                                             ④ 복호화하고 껍데기 제거
                                                  ↓
                                             wg0 ── ⑤ 앱에 전달
```

**애플리케이션은 터널의 존재를 모른다.** `10.10.0.2`로 보냈더니 그냥 도착한 것이다.
kubelet도 etcd도 apiserver도 평범한 사설망에 있다고 믿고 동작한다.

## 왜 WireGuard인가 (다른 VPN과 비교)

| | WireGuard | OpenVPN | IPsec |
|---|---|---|---|
| 코드 크기 | **~4,000줄** | ~100,000줄 | ~400,000줄 |
| 위치 | 리눅스 커널 내장 (5.6+) | 유저스페이스 | 커널 |
| 설정 파일 | 10~15줄 | 수십~수백 줄 | 매우 복잡 |
| 암호 협상 | **없음** (고정) | 협상 | 협상 |

코드가 작다는 것은 **전수 감사가 가능한 크기**라는 뜻이다. 취약점이 숨을 곳이 적다.

암호 협상이 없는 것도 핵심 설계다. OpenVPN이나 IPsec은 양쪽이 "무슨 암호를 쓸까"를
협상하는데, 여기서 다운그레이드 공격과 설정 실수가 나온다.
WireGuard는 ChaCha20, Poly1305, Curve25519, BLAKE2s로 **못 박아뒀다.**
고를 것이 없으니 잘못 고를 수도 없다. 깨지면 프로토콜 버전을 올려 교체한다.

## 설정 구조 — SSH와 닮았다

키 쌍을 만들고 **상대의 공개키를 등록**해 신원을 확인한다. `authorized_keys`와 같은 발상이다.

```ini
[Interface]                          # 나 자신
Address    = 10.10.0.1/24                # 터널에서 내 주소
ListenPort = 51820
PrivateKey = <내 개인키>

[Peer]                               # 상대방 (여러 개 가능)
PublicKey  = <상대 공개키>               # ← 신원
Endpoint   = 198.51.100.22:51820        # ← 실제로 어디로 보낼지
AllowedIPs = 10.10.0.0/24               # ← 어떤 대역을 이 상대가 담당하는지
PersistentKeepalive = 25
```

## ⭐ Cryptokey Routing — 가장 중요한 개념

보통 방화벽과 라우팅 테이블은 따로 놀지만, WireGuard는 **`AllowedIPs` 하나가 둘 다 한다.**

1. **송신 라우팅** — 이 대역으로 갈 패킷은 이 공개키의 상대에게 보낸다
2. **수신 필터** — 이 상대가 보낸 패킷인데 출발지가 이 대역이 아니면 **버린다**

즉 "공개키 ↔ IP 대역" 대응표가 곧 라우팅 테이블이자 접근제어 목록이다.
암호학적 신원과 네트워크 주소가 하나로 묶여 있어서, IP를 위조해도 개인키가 없으면 아무것도 못 한다.

> **2번이 함정이다.** 파드 트래픽(`10.244.0.0/16`)을 터널에 그냥 태우려 하면
> `AllowedIPs`에 없어서 **로그도 없이 조용히 폐기된다.**
>
> 해결책은 두 가지다.
> - CNI를 **VXLAN Always**로 두어 바깥 헤더 출발지를 `10.10.0.x`로 만든다 (권장)
> - `AllowedIPs`에 파드 대역을 추가한다

## 포트 51820

- **WireGuard의 관례적 기본 포트.** IANA 공식 할당이 아니라 프로젝트가 정한 값이다
- **아무 포트나 써도 된다.** `ListenPort = 40000`으로 바꿔도 동일하게 동작한다
- 인터페이스를 여러 개 만들면 51821, 51822... 로 이어 쓴다
- **UDP만 쓴다.** TCP 모드가 아예 없다

TCP 모드가 없는 것은 의도적이다. 터널 안에서 TCP가 도는데 터널 자체도 TCP면
재전송 제어가 이중으로 걸려 성능이 무너진다 (TCP-over-TCP meltdown).

→ `ss`로 확인할 때 `-u`가 필요한 이유. `ss -lntp`로는 절대 안 보인다.

## 그 밖의 성질

- **연결 개념이 없다.** TCP처럼 접속/종료가 없고 패킷만 오간다.
  노드가 재부팅해도 알아서 복구되고, IP가 바뀌어도(로밍) 따라간다
- **조용하다.** 인증되지 않은 패킷에 일절 응답하지 않아 포트 스캔으로 존재를 알 수 없다
- **상태 판단은 handshake 시각으로.** "연결됨/끊김" 표시가 없으므로
  `sudo wg show`에 찍힌 마지막 핸드셰이크 시각이 유일한 근거다

> ⚠️ **터널을 올린 뒤에는 `nc`로 포트를 못 찔러본다.** 응답을 안 하기 때문이다.
> 보안 목록 검증은 **터널을 올리기 전에** 해둬야 한다.

## 검토 메모

### 이 문제에 맞는 이유

[노드 주소 문제](../concepts/02_node-addressing.md)에서 필요한 것은 연결이 아니라
**양쪽 인터페이스에 실제로 존재하면서 서로 닿는 주소**다.
`wg0`의 `10.10.0.1`이 정확히 그 조건을 만족한다.

부수 효과:

- OCI에서 열 포트가 `udp/51820` 하나, 소스 IP도 상대 한 대로 한정
- 파드 간 트래픽이 암호화된다 (control plane은 이미 TLS지만 오버레이는 평문)

### 비용과 우려

| 항목 | 내용 |
|---|---|
| **계층 증가** | 장애 시 "wg 문제인가 k8s 문제인가"를 먼저 갈라야 한다 |
| **MTU** | `wg0` 기본 MTU 1420. 그 안에 VXLAN(50바이트)이 또 들어가면 파드 MTU ~1370.<br>CNI MTU를 맞춰주지 않으면 **큰 패킷만 멈추는** 진단하기 어려운 장애가 난다 |
| **단일 장애점** | 터널이 끊기면 클러스터가 통째로 분리된다 |
| **정석이 아님** | 네트워크 토폴로지가 깨져서 쓰는 우회책이지 베스트 프랙티스가 아니다 |

### 대안

| 대안 | 평가 |
|---|---|
| **한쪽 VCN 재생성** | 겹치지 않는 CIDR로 다시 만들고 피어링. **가장 정석.**<br>인스턴스 재생성이 필요할 수 있어 비용을 확인해야 한다 |
| **두 노드를 같은 VCN으로** | 근본 해결. 마이그레이션 부담 |
| **보안 목록 전체 개방** | ❌ 주소 문제가 해결되지 않는다. 애초에 성립하지 않음 |
| **Calico 내장 WireGuard** | 파드 트래픽만 암호화. 주소 문제는 그대로 남음 |
| **k8s-2 한 대만 사용** | 32C/251G에 `/dev/kvm`이 있으므로 그 위에 VM으로 3노드 클러스터 구성.<br>**네트워크 문제가 통째로 사라지고** HA·업그레이드 실습까지 가능.<br>CKA 목적만 보면 오히려 유리할 수 있다 |

### 결정 전에 답해볼 질문

1. 두 VCN이 **같은 테넌시**인가? (콘솔 확인 필요) 같다면 한쪽 재생성 후 피어링이 가장 깨끗하다.
2. 인스턴스를 재생성해도 되는가? 데이터·설정 손실이 있는가?
3. 목적이 **CKA 대비**라면, 물리 2노드를 굳이 이어야 하는가?
   k8s-2 단독 + VM 3노드가 시험 범위(HA, 업그레이드, etcd 복구)를 더 넓게 덮는다.
4. 터널 계층이 늘어나는 진단 복잡도를 감수할 만한가?
   — 반대로 그 자체가 학습 소재라는 관점도 있다.
