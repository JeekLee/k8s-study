# 검토 자료

기술 자료와 그 판단 근거. **Phase 0 연결 방식은 결정됐다** (2026-09-10).

> ### ✅ 결정 — 호스트 간 WireGuard + VM 서브넷 라우팅
> 두 호스트를 하이퍼바이저로 쓰고 그 위의 VM 6대로 클러스터를 만든다.
> 두 후보의 장점을 합친 형태다 — 중첩 VM으로 노드를 늘리고, 터널로 두 호스트를 잇는다.
> 설계는 [`docs/01-network-design.md`](../../../docs/01-network-design.md),
> 절차는 [`docs/02-roadmap.md`](../../../docs/02-roadmap.md) Stage 8.

## 결정해야 할 것 — Phase 0 노드 간 연결 방식

두 노드가 서로 다른 VCN에 있고 사설 대역이 `10.0.0.0/24`로 겹친다.
그 결과 [노드 주소 문제](../concepts/02_node-addressing.md)가 생겨 클러스터가 성립하지 않는다.

### 후보

| 후보 | 접근 | 문서 | 상태 |
|---|---|---|---|
| **WireGuard 오버레이** | 깨진 환경을 고쳐 쓴다 | [`wireguard.md`](wireguard.md) | ✅ **채택** (호스트 간) |
| **중첩 VM 클러스터** | 안 깨진 환경을 새로 만든다 | [`nested-vm.md`](nested-vm.md) | ✅ **채택** (양쪽 호스트) |
| 한쪽 VCN 재생성 | 문제의 원인을 제거한다 | — | 테넌시 확인 필요 |
| 보안 목록 전체 개방 | — | — | ❌ **제외** |

> 보안 목록 전체 개방이 제외된 이유: 포트를 다 열어도 주소 문제가 그대로 남아
> `kubectl logs`·`exec`가 동작하지 않는다. 선택지가 아니라 애초에 성립하지 않는 안이다.

### 한눈에 비교

| | WireGuard | 중첩 VM |
|---|---|---|
| 물리 노드 사용 | 2대 모두 | k8s-2만 (k8s-1 유휴) |
| control plane | 1대 (HA 불가) | **3대 (진짜 HA)** |
| 네트워크 설정 | 터널 구성 필요 | 불필요 |
| 스냅샷 롤백 | ❌ | ✅ |
| 계층 복잡도 | +1 (터널) | +1 (가상화) |
| CKA 범위 커버 | 보통 | **넓음** |
| 학습 소재 | 네트워크 심화 | 클러스터 운영 |

### 결정 기준

목적이 **CKA 대비**라는 점을 기준으로 보면 중첩 VM이 시험 범위를 더 넓게 덮는다.
반면 **네트워크를 깊이 이해하는 것**이 목적이라면 WireGuard 쪽이 배울 것이 많다.

두 문서 하단의 「검토 메모」에 각각의 판단 질문을 정리해 두었다.
순차적으로 둘 다 하는 선택지도 있다.
