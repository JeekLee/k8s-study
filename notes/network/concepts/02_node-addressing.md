# 노드 주소 문제 — 왜 포트를 다 열어도 안 되는가

> 이 프로젝트에서 가장 이해가 어려웠던 부분. Phase 0의 모든 판단이 여기서 나온다.

## 오해 — "포트만 열면 되는 거 아닌가?"

합리적인 생각이고, **연결 자체는 실제로 된다.** 이미 확인했다:

```bash
nc -vz -w3 198.51.100.22 22
# → Connection to 198.51.100.22 22 port [tcp/ssh] succeeded!
```

보안 목록에서 6443을 열면 k8s-1은 k8s-2의 6443으로 TCP 연결을 맺을 수 있다. 문제없다.

**그런데 클러스터는 깨진다.** 문제는 연결이 아니라 **주소**이기 때문이다.

> 포트를 여는 것은 **문을 여는 것**이고, 주소는 **그 문이 어디 있는지 알려주는 것**이다.
> 문을 다 열어놔도 상대가 엉뚱한 주소로 찾아가면 만나지 못한다.

## 쿠버네티스는 주소를 "등록"하고 나중에 "꺼내 쓴다"

kubelet은 시작할 때 자기 IP를 apiserver에 보고하고, apiserver가 그것을 etcd에 저장한다.
(kubelet이 etcd에 직접 쓰는 것이 아니다 → [`../../kubernetes/etcd.md`](../../kubernetes/etcd.md))

```bash
kubectl get nodes -o wide
# NAME    STATUS   INTERNAL-IP    ← 이 값이 etcd에 저장된 주소
```

이후 `kubectl logs`를 치면 이런 일이 벌어진다:

```
kubectl → apiserver → (etcd에서 노드 주소 조회) → 그 주소의 10250 포트로 직접 접속
```

**apiserver가 등록된 주소로 직접 접속한다.** 그래서 등록되는 주소는 두 조건을 동시에 만족해야 한다.

1. 노드의 **실제 인터페이스에 붙어 있을 것** (kubelet이 바인딩해야 하므로)
2. **상대 노드에서 닿을 것**

## 핵심 — 노드는 자기 공인 IP를 모른다

```bash
ip addr show ens3
# → inet 10.0.0.155/24
```

`203.0.113.11`은 **어디에도 없다.** OCI가 인스턴스 *바깥에서* 1:1 NAT로 변환하기 때문에,
노드 본인은 자기 공인 주소를 알 방법이 없다.

tcpdump에서 목적지가 사설 IP로 찍히는 것이 이것을 보여준다:

```
IP 203.0.113.11.54321 > 10.0.0.169.51820: UDP, length 6
                        └─ 공인 IP가 아님 ─┘
```

그래서 "너 IP 뭐야?"라고 물으면 노드는 **`10.0.0.155`라고 답할 수밖에 없다.**

## 두 경우를 나란히

**같은 VCN**

```
k8s-2 kubelet : "내 주소는 10.0.0.169"  → etcd 저장
k8s-1 apiserver: etcd에서 10.0.0.169 조회 → 접속 → ✅ 도착
```

**다른 VCN + 모든 포트 개방**

```
k8s-2 kubelet : "내 주소는 10.0.0.169"  → etcd 저장   ← 이렇게 말할 수밖에 없음
k8s-1 apiserver: etcd에서 10.0.0.169 조회 → 접속 → ❌ 자기 VCN에서 찾다 실패
```

**포트는 전부 열려 있는데도 실패한다.**
아무도 `198.51.100.22`로 접속을 시도하지 않기 때문이다. 그 주소는 etcd 어디에도 없다.
열어둔 문 앞에 아무도 오지 않는 것이다.

## 우회 시도와 실패

### A안 — 사설 IP로 등록

```bash
--node-ip=10.0.0.169
```

노드는 붙고 `kubectl get nodes`도 `Ready`로 나온다. **여기서 속는다.** 그런데:

```bash
kubectl logs mypod
# Error: dial tcp 10.0.0.169:10250: i/o timeout
```

`logs`, `exec`, `port-forward`, 메트릭이 전부 죽는다. 파드 스케줄링 같은 기본 동작은
apiserver를 향하는 단방향이라 되지만, **apiserver → kubelet 방향이 필요한 모든 기능**이 실패한다.

### B안 — 공인 IP로 등록

```bash
--node-ip=203.0.113.11
--apiserver-advertise-address=203.0.113.11
```

kubelet이 거부한다. 자기 인터페이스 목록에서 그 주소를 찾지 못하기 때문이다.
없는 주소를 자기 것이라고 등록할 수는 없다.

CNI도 마찬가지다. Calico가 VXLAN 종단점(VTEP)을 만들려고 그 주소에 바인딩하려다 실패한다.

### 막다른 골목

> **등록 가능한 주소는 닿지 않고, 닿는 주소는 등록이 안 된다.**

## 정리 — 두 주소의 일치 문제

| | 노드가 자기를 소개하는 주소 | 남이 그 노드에 닿는 주소 | 일치? |
|---|---|---|---|
| 같은 VCN | `10.0.0.169` | `10.0.0.169` | ✅ |
| 다른 VCN + 전체 개방 | `10.0.0.169` | `198.51.100.22` | ❌ |
| 오버레이 터널 사용 시 | `10.10.0.2` | `10.10.0.2` | ✅ |

쿠버네티스는 **"노드가 스스로 등록한 주소로 다른 노드가 접속한다"**는 전제 위에 돌아간다.
그 전제가 깨지면 포트를 아무리 열어도 소용없다.

## 그래서 필요한 것

**연결이 아니라 주소를 만드는 것.** 두 노드가 공유하는, 양쪽 인터페이스에 실제로 존재하면서
서로 닿는 주소 공간이 필요하다.

오버레이 터널(WireGuard 등)이 하는 일이 정확히 이것이다 — VCN을 이어붙이는 것이 아니라
**어느 VCN에도 속하지 않는 제3의 네트워크를 새로 만든다.**

```
        VCN-A                              VCN-B
    (10.0.0.0/24)                      (10.0.0.0/24)
         │                                   │
    [k8s-1] ens3 10.0.0.155        [k8s-2] ens3 10.0.0.169
         │                                   │
         └───── 공용 인터넷 (UDP) ───────────┘
         │                                   │
       wg0 10.10.0.1  ←── 새 네트워크 ──→  wg0 10.10.0.2
                      (10.10.0.0/24)
```

`10.10.0.0/24`는 어느 VCN에도 속하지 않고 **두 노드에만 존재**한다.
`wg0`는 커널이 만든 진짜 인터페이스라 `ip addr`에 나오고, 바인딩할 수 있고, 상대에서 닿는다.

| | 인터페이스에 있나 | 상대에서 닿나 |
|---|---|---|
| `10.0.0.155` (사설) | ✅ | ❌ |
| `203.0.113.11` (공인) | ❌ | ✅ |
| **`10.10.0.1` (터널)** | ✅ | ✅ |

> **연결은 원래 된다. 없는 것은 주소다.**
