# 학습 로드맵 — 개요

클러스터를 세우는 과정 자체를 CKA 학습 경로로 삼는다.
각 단계는 앞 단계가 **동작한다는 전제** 위에 서 있다. 완료 기준을 통과해야 다음으로 간다.

**단계별 상세는 [`stages/`](stages/)에 있다.**

## 최종 목표

| 항목 | 값 |
|---|---|
| 구성 | **6노드** — control plane 3 + worker 3 |
| 호스트 | k8s-1 + k8s-2 (둘 다 하이퍼바이저 역할만, 클러스터에 미참여) |
| 노드 간 연결 | WireGuard 사이트 간 터널 + 서브넷 라우팅 |
| 버전 | Kubernetes v1.35 · containerd 2.2.2 · Calico |
| 예상 기간 | 6–10주 (병행 학습 기준) |

## 순서에 대한 판단

**네트워크 작업을 Stage 4로 미뤘다.** k8s-2 안에서만 클러스터를 만들면
네트워크가 저절로 되므로, 터널 없이 Stage 3까지 갈 수 있고
**훨씬 빨리 동작하는 클러스터를 손에 넣는다.**

부수 효과로 **Stage 3까지는 단일 호스트 구성과 완전히 공통**이다.
나중에 크로스 호스트를 포기해도 Stage 1–3은 그대로 쓰인다.

## 대역 설계

전부 서로소여야 한다.

| 대역 | 값 | 용도 |
|---|---|---|
| 호스트 VCN | `10.0.0.0/24` | 양쪽 동일하지만 라우팅하지 않으므로 무관 |
| WireGuard 터널 | `10.10.0.0/24` | 호스트끼리만 |
| k8s-1 VM | `192.168.121.0/24` | Stage 4 |
| k8s-2 VM | `192.168.122.0/24` | Stage 1 |
| 파드 | `10.244.0.0/16` | Stage 2 |
| 서비스 | `10.96.0.0/12` | = 10.96.0.0 ~ 10.111.255.255 |

## 노드 배치와 이름 규칙

이름은 **`<호스트><번호>-<역할><번호>`** 형식이다. 그대로 쿠버네티스 노드 이름이 되므로
소문자와 하이픈만 쓴다.

```
k2-cp1
│  └── 역할(cp = control plane, w = worker) + 호스트 내 번호
└───── 어느 하이퍼바이저에 있는가 (k1 = k8s-1, k2 = k8s-2)
```

| 호스트 | VM | 역할 | 주소 | MAC |
|---|---|---|---|---|
| k8s-2 | **`k2-cp1`** | control plane | 192.168.122.11 | `52:54:00:00:02:11` |
| k8s-2 | `k2-w1` | worker | 192.168.122.21 | `52:54:00:00:02:21` |
| k8s-2 | `k2-w2` | worker | 192.168.122.22 | `52:54:00:00:02:22` |
| k8s-1 | `k1-cp1` | control plane | 192.168.121.11 | `52:54:00:00:01:11` |
| k8s-1 | `k1-cp2` | control plane | 192.168.121.12 | `52:54:00:00:01:12` |
| k8s-1 | `k1-w1` | worker | 192.168.121.21 | `52:54:00:00:01:21` |

**`k2-cp1`이 Stage 2에서 가장 먼저 만드는 노드다.** Stage 1~3이 k8s-2에서만 이뤄지므로
첫 클러스터는 `k2-cp1` + `k2-w1` + `k2-w2` 3노드로 구성되고,
Stage 4~5에서 k8s-1의 3대가 합류한다.

### 이름에 호스트를 넣는 이유

`kubectl get nodes`만 봐도 **장애 도메인이 드러난다.**

```
NAME     STATUS   ROLES           AGE
k1-cp1   Ready    control-plane   ...   ┐
k1-cp2   Ready    control-plane   ...   ├ k8s-1 (CP 2대)
k1-w1    Ready    <none>          ...   ┘
k2-cp1   Ready    control-plane   ...   ┐
k2-w1    Ready    <none>          ...   ├ k8s-2 (CP 1대)
k2-w2    Ready    <none>          ...   ┘
```

Stage 5의 쿼럼 실험에서 "어느 호스트를 죽이면 클러스터가 멈추는가"가 한눈에 보인다.
**k8s-1이 죽으면 CP가 1대만 남아 쿼럼(2)이 깨진다.**

### 주소·MAC 규칙

| 자리 | 의미 |
|---|---|
| 대역 3옥텟 `121` / `122` | 호스트 (k8s-1 / k8s-2) |
| 주소 4옥텟 `11~19` | control plane |
| 주소 4옥텟 `21~29` | worker |
| MAC 5옥텟 `01` / `02` | 호스트 |
| MAC 6옥텟 | 주소 4옥텟과 동일 |

`52:54:00`은 QEMU/KVM에 할당된 MAC 접두사다.
MAC은 libvirt 네트워크 XML의 DHCP 예약과 **반드시 일치**해야 한다.

## 미리 알고 갈 두 가지

**HAProxy를 Stage 2에서 세운다.** control plane이 Stage 5에서 3대가 되므로
`--control-plane-endpoint`가 필요한데, 나중에 바꾸려면 **인증서를 전부 재발급**해야 한다.

**MTU를 Stage 2부터 1370으로 잡는다.** Stage 4에서 캡슐화가 두 겹이 된다
(`wg0` 1420 → VXLAN −50). 맞추지 않으면 **작은 요청은 되는데 큰 응답만 멈추는**
진단하기 어려운 장애가 난다.

여기에 더해, 이 환경의 `ens3`는 **MTU 9000**(점보 프레임)이라
`wg-quick`이 MTU를 자동 계산하면 8920을 잡는다. 공용 인터넷 경로는 1500이므로
WireGuard 설정에 **`MTU = 1420`을 명시**해야 한다.
→ [`notes/network/concepts/03_interfaces.md`](../notes/network/concepts/03_interfaces.md)

## 진행 원칙

1. **완료 기준을 통과해야 다음 단계로.** Stage 2에서 대충 넘긴 것은 Stage 4에서 두 배로 돌아온다.
2. **명령을 붙여넣기 전에 왜 그 값인지 적는다.** 특히 IP 대역과 포트.
3. **막힌 것은 지우지 않는다.** 실패 기록이 배점 30%짜리 영역의 학습 자료다.
4. **스냅샷을 습관화한다.** Stage 1 이후로는 무엇을 하든 먼저 스냅샷을 찍는다.
5. **Stage 3까지는 방향 확정 없이 진행 가능하다.**
