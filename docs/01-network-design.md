# Phase 0 — 네트워크 설계

> **이 문서의 목적**은 명령어 목록이 아니다.
> "왜 노드가 서로 안 보이는가"를 스스로 진단하고, 선택지를 비교해 결정하고, 그 결정을 검증하는 과정 전체가 학습 대상이다.
> 쿠버네티스 트러블슈팅의 절반은 결국 네트워크다.

---

## 1. 문제 정의

두 노드에 SSH는 되는데, **서로는 닿지 않는다.**

### 실측 데이터

```
k8s-1 → 10.0.0.169  (k8s-2 사설)      2 packets transmitted, 0 received, 100% loss
k8s-2 → 10.0.0.155  (k8s-1 사설)      2 packets transmitted, 0 received, 100% loss
k8s-1 → 198.51.100.22:22   (공인)    OPEN
k8s-1 → 198.51.100.22:51820 (공인)   BLOCKED
```

### 노드가 보는 자기 네트워크

```
# k8s-1
ens3   10.0.0.155/24
default via 10.0.0.1 dev ens3

# k8s-2
ens3   10.0.0.169/24
default via 10.0.0.1 dev ens3
```

<details>
<summary>❓ 먼저 스스로 생각해볼 것 — 무엇이 이상한가?</summary>

두 노드가 **같은 `10.0.0.0/24`** 대역에 있고, 게이트웨이 주소마저 `10.0.0.1`로 동일하다.
그런데 서로 핑이 안 간다.

같은 서브넷이면 L2로 바로 닿아야 한다. 안 닿는다는 건 **같은 서브넷이 아니라는 뜻**이다.
즉 두 개의 서로 다른 네트워크가 우연히 같은 사설 대역을 쓰고 있다.
</details>

### 원인

`10.0.0.0/24`는 [RFC 1918](https://datatracker.ietf.org/doc/html/rfc1918) 사설 대역이고, OCI가 VCN을 만들 때 기본값으로 자주 잡는 값이다.
두 노드는 **서로 다른 VCN**(아마도 다른 리전 또는 다른 테넌시)에 있고, 각 VCN이 독립적으로 같은 CIDR를 할당했다.

사설 IP는 VCN 안에서만 의미가 있다. `10.0.0.169`로 보낸 패킷은 **k8s-1 자신의 VCN 안에서** 그 주소를 찾다가 버려진다.

> 💡 **핵심** — 사설 IP는 전역 고유하지 않다. "같은 대역에 있다"는 것과 "같은 네트워크에 있다"는 것은 전혀 다른 얘기다.

방화벽 문제도 아니다. 로컬 iptables는 통과시킨다:

```
Chain INPUT (policy ACCEPT)
1  ACCEPT  all   state RELATED,ESTABLISHED
2  ACCEPT  icmp
3  ACCEPT  all              ← 전부 허용
4  ACCEPT  tcp  dpt:22
5  REJECT  all   reject-with icmp-host-prohibited
```

3번 규칙이 5번보다 먼저 전부 허용하므로, 차단 지점은 노드 바깥 — **OCI 보안 목록(Security List)** 이다.

## 2. 쿠버네티스가 요구하는 통신

지금 열린 건 `tcp/22` 하나뿐인데, 클러스터는 이만큼을 필요로 한다.

| 포트 | 프로토콜 | 방향 | 용도 |
|---|---|---|---|
| 6443 | TCP | → control plane | kube-apiserver |
| 2379–2380 | TCP | control plane 내부 | etcd 클라이언트 / 피어 |
| 10250 | TCP | 모든 노드 | kubelet API (`logs`, `exec`, 메트릭) |
| 10256 | TCP | 모든 노드 | kube-proxy 헬스체크 |
| 30000–32767 | TCP | 모든 노드 | NodePort 서비스 |
| 4789 / 8472 | UDP | 모든 노드 | VXLAN 오버레이 (CNI에 따라) |
| — | IP proto 4 | 모든 노드 | IPIP (Calico 기본 모드 사용 시) |

여기에 **파드 간 트래픽**이 더해진다. 쿠버네티스 네트워크 모델은 "모든 파드가 NAT 없이 서로 통신 가능"을 전제로 하기 때문에, 노드 간 경로가 뚫려 있지 않으면 클러스터는 성립하지 않는다.

## 3. 선택지 비교

### A. OCI 보안 목록을 직접 개방

위 표의 포트를 상대 공인 IP에 대해 전부 연다.

- ✅ 추가 소프트웨어 없이 가장 빠름
- ❌ **etcd와 apiserver가 인터넷에 노출된다**
- ❌ 노드 간 트래픽(파드 통신, kubelet)이 **평문으로 공용망을 지난다**
- ❌ 열어야 할 규칙이 많아 실수 여지가 큼 (특히 NodePort 32768개)

### B. VCN 피어링

OCI 레벨에서 두 VCN을 연결한다.

- ✅ 가장 정석. 사설 IP로 직접 통신
- ❌ **같은 테넌시여야 한다.** 공인 IP 대역이 완전히 달라 다른 리전/계정일 가능성이 높음
- ❌ **결정적 문제: 양쪽 CIDR가 `10.0.0.0/24`로 동일하다.** 피어링은 중복 CIDR를 허용하지 않는다. 한쪽 VCN을 다른 대역으로 재생성해야 한다

### C. WireGuard 오버레이 ← **채택**

공인 IP 위에 암호화 터널을 만들고, 클러스터는 **터널 IP로만** 구성한다.

- ✅ OCI에서 열 포트가 **`udp/51820` 하나**, 그것도 상대 IP 한정
- ✅ 노드 간 모든 트래픽이 암호화됨 (etcd, kubelet, 파드 통신 전부)
- ✅ 기저 IP가 바뀌어도 터널 IP는 그대로 → 클러스터 설정이 안 흔들린다
- ✅ 커널 모듈이라 오버헤드가 작음
- ⚠️ 계층이 하나 늘어난다 — 장애 시 "wg인가 k8s인가"를 가릴 줄 알아야 한다 (이것도 학습거리)

> ### ✅ 결정: C — WireGuard 사이트 간 터널
>
> 단, 단순한 2노드 연결이 아니라 **두 호스트를 하이퍼바이저로 쓰고 그 위의 VM들을 잇는** 형태로 확장한다.

A안(보안 목록 전체 개방)은 검토에서 제외됐다. 포트를 다 열어도
[노드 주소 문제](../notes/network/concepts/02_node-addressing.md)가 그대로 남아 클러스터가 성립하지 않는다.

B안(VCN 재생성)은 CIDR 중복 때문에 인스턴스 재생성이 필요해 비용이 크다.

### 최종 구성

두 호스트에 KVM 중첩 가상화가 가능함을 확인했고(`vmx` 노출, `/dev/kvm` 존재),
각 호스트 위에 VM을 띄워 **6노드 클러스터**를 만든다.

```
        k8s-1 (16C/125G)                      k8s-2 (32C/251G)
        하이퍼바이저                            하이퍼바이저
   virbr0 192.168.121.0/24              virbr0 192.168.122.0/24
     ├─ k1-cp1  .121.11                   ├─ k2-cp1  .122.11
     ├─ k1-cp2  .121.12                   ├─ k2-w1   .122.21
     └─ k1-w1   .121.21                   └─ k2-w2   .122.22
              │                                      │
         wg0 10.10.0.1 ◄─── UDP 51820 ───► wg0 10.10.0.2
```

두 호스트에는 쿠버네티스를 설치하지 않는다. **VM들만 클러스터 멤버**다.
호스트는 터널 종단이자 라우터 역할만 한다.

이 방식의 근거와 대안 비교는 [`notes/network/reference/`](../notes/network/reference/README.md)에 남아 있다.
단계별 구축 절차는 [`02-roadmap.md`](02-roadmap.md) Stage 4를 따른다.

## 4. 대역 설계

겹치면 라우팅이 조용히 깨진다. 네 개 대역이 **모두 서로소**여야 한다.

| 대역 | 값 | 범위 | 비고 |
|---|---|---|---|
| 호스트(VCN) | `10.0.0.0/24` | 10.0.0.0 – 10.0.0.255 | 양쪽 동일하지만 **라우팅하지 않으므로 무관** |
| WireGuard 터널 | `10.10.0.0/24` | 10.10.0.0 – 10.10.0.255 | 호스트끼리만. k8s-1 = `.1`, k8s-2 = `.2` |
| k8s-1 VM | `192.168.121.0/24` | | libvirt 기본값에서 **변경** |
| k8s-2 VM | `192.168.122.0/24` | | libvirt 기본값 |
| 파드 | `10.244.0.0/16` | 10.244.0.0 – 10.244.255.255 | `--pod-network-cidr` |
| 서비스 | `10.96.0.0/12` | 10.96.0.0 – **10.111**.255.255 | `--service-cidr` (기본값) |

<details>
<summary>❓ <code>10.96.0.0/12</code>의 실제 범위를 직접 계산해볼 것</summary>

`/12`는 상위 12비트가 고정 → 두 번째 옥텟은 상위 4비트만 고정된다.
`96 = 0110 0000` → 상위 4비트 `0110` 고정, 하위 4비트는 자유 → `0110 0000`(96) ~ `0110 1111`(111).

따라서 **10.96.0.0 – 10.111.255.255**.
`10.10.x`도 `10.244.x`도 이 범위 밖이므로 안전하다.
서비스 대역을 무심코 `10.0.0.0/12`로 잡으면 호스트 대역과 정면충돌한다.
</details>

## 5. 구성

> 아래는 **호스트 간 터널** 구성이다.
> 여기에 VM 대역 라우팅(`AllowedIPs` 확장 + `ip_forward` + FORWARD 규칙)을 더하면
> 크로스 호스트 클러스터가 된다. 전체 절차는 [`02-roadmap.md`](02-roadmap.md) Stage 4 참고.


### 5-1. OCI 보안 목록 (콘솔 작업)

양쪽 VCN에 인그레스 규칙을 하나씩 추가한다. **소스를 상대 노드 IP로 한정**하는 것이 핵심이다.

| VCN | Source CIDR | 프로토콜 | 포트 |
|---|---|---|---|
| k8s-1 쪽 | `198.51.100.22/32` | UDP | 51820 |
| k8s-2 쪽 | `203.0.113.11/32` | UDP | 51820 |

### 5-2. 키 생성 (양쪽 노드)

```bash
sudo apt-get update && sudo apt-get install -y wireguard
umask 077
wg genkey | sudo tee /etc/wireguard/privatekey | wg pubkey | sudo tee /etc/wireguard/publickey
```

> `umask 077`을 먼저 거는 이유: 개인키가 한순간이라도 world-readable로 존재하면 안 된다.
> `wg-quick`은 설정 파일 권한이 느슨하면 경고를 낸다.

### 5-3. 터널 설정

**k8s-1** — `/etc/wireguard/wg0.conf`

```ini
[Interface]
Address    = 10.10.0.1/24
ListenPort = 51820
PrivateKey = <k8s-1 개인키>

[Peer]
PublicKey  = <k8s-2 공개키>
Endpoint   = 198.51.100.22:51820
AllowedIPs = 10.10.0.0/24
PersistentKeepalive = 25
```

**k8s-2** — `/etc/wireguard/wg0.conf`

```ini
[Interface]
Address    = 10.10.0.2/24
ListenPort = 51820
PrivateKey = <k8s-2 개인키>

[Peer]
PublicKey  = <k8s-1 공개키>
Endpoint   = 203.0.113.11:51820
AllowedIPs = 10.10.0.0/24
PersistentKeepalive = 25
```

```bash
sudo systemctl enable --now wg-quick@wg0
```

<details>
<summary>❓ <code>AllowedIPs</code>는 무엇을 의미하는가? (WireGuard에서 가장 많이 틀리는 부분)</summary>

`AllowedIPs`는 두 가지 역할을 **동시에** 한다.

1. **송신 라우팅** — 이 대역으로 가는 패킷을 이 피어에게 보낸다
2. **수신 필터** — 이 피어에게서 온 패킷 중 출발지가 이 대역이 아니면 **버린다**

2번이 함정이다. 나중에 파드 트래픽(`10.244.0.0/16`)을 터널에 그냥 태우려 하면, `AllowedIPs`에 없어서 조용히 폐기된다.
로그도 안 남는다. — 이것이 Phase 3에서 **VXLAN 캡슐화가 필요한 이유**다.
캡슐화하면 바깥 헤더의 출발지가 `10.10.0.x`가 되어 필터를 통과한다.

`PersistentKeepalive = 25`는 양쪽이 NAT 뒤에 있을 때 세션을 살려두기 위한 것이다.
</details>

## 6. 검증

순서대로 통과해야 다음 Phase로 간다.

```bash
# 1. 터널이 올라왔는가 — handshake 시각이 찍혀야 한다
sudo wg show

# 2. 터널 IP로 닿는가
ping -c3 10.10.0.2

# 3. 지연이 실용적인가 (공용망을 지나므로 확인 필요)
ping -c20 10.10.0.2 | tail -2

# 4. TCP도 통하는가 (etcd는 ICMP가 아니라 TCP를 쓴다)
#    k8s-2에서:  nc -l 6443
#    k8s-1에서:
nc -vz 10.10.0.2 6443

# 5. 재부팅 후에도 살아나는가
sudo systemctl is-enabled wg-quick@wg0
```

> ⚠️ 3번을 그냥 넘기지 말 것. etcd는 디스크 fsync와 **피어 지연**에 민감하다.
> RTT가 크거나 튀면 단일 control plane에서는 문제없지만, Phase 4에서 HA를 구성할 때 영향이 있다. 지금 측정해서 기록해 둔다.

## 7. 막혔을 때 — 진단 순서

계층을 아래에서 위로 하나씩 좁힌다. 이 순서 자체가 CKA Troubleshooting의 사고방식이다.

| 증상 | 확인 | 의미 |
|---|---|---|
| handshake가 안 찍힘 | `sudo wg show` | 패킷이 상대에 도달조차 못함 |
| ↳ | `sudo ss -lunp \| grep 51820` | 데몬이 포트를 잡고 있는가 |
| ↳ | `sudo tcpdump -ni ens3 udp port 51820` | 나가는가 / 들어오는가 |
| ↳ | 나가지만 안 들어옴 | **OCI 보안 목록** 또는 상대 방화벽 |
| handshake는 되는데 핑 실패 | `ip addr show wg0`, `ip route` | 주소·라우팅 문제 |
| ↳ | `AllowedIPs` 확인 | 수신 필터에 걸려 폐기 중 |
| 간헐적 끊김 | `PersistentKeepalive` | NAT 세션 만료 |

## 8. 정리하며 답해볼 질문

2. 방화벽 차단 지점이 노드 로컬이 아니라 클라우드 레벨임을, iptables 규칙만 보고 어떻게 판단했는가?
3. `AllowedIPs`의 두 가지 역할 중 어느 쪽이 파드 트래픽에서 문제가 되며, 어떻게 우회하는가?
4. 서비스 대역을 `10.96.0.0/12`로 두는 것이 왜 안전한가? 직접 범위를 계산해 확인했는가?
5. 이 설계에서 **단일 장애점**은 무엇인가? WireGuard 터널이 끊기면 클러스터는 어떤 상태가 되는가?
